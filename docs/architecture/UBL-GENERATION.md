# R3 UBL Document Generation Engine (Phase 6)

`UblInvoiceGenerator` turns a posted `SalesInvoice` + its already-routed
`ElectronicDocument` into a real UBL 2.1 / UBL-TR invoice XML string - no
placeholder or fabricated field is ever emitted; anything R3 doesn't
actually model is either omitted (and documented below) or throws
`UblGenerationException` rather than guessing.

## Architecture

```
ElectronicDocument (Ready)
        │
        ▼
UblInvoiceGenerator.Generate(electronicDocumentId)
        │  reads: sales_documents, sales_document_lines, products, units,
        │         companies, electronic_document_company_profiles,
        │         accounts, account_tax_profiles, account_addresses,
        │         account_einvoice_profiles
        ▼
   UBL XML string  ── structural Validate() ──▶ throws UblGenerationException on failure
        │
        ▼ (caller composes these three calls explicitly - no hidden orchestrator)
LocalElectronicDocumentService.SavePayload(id, UblXml, xml, ...)
LocalElectronicDocumentService.Generate(id, userId)   // Ready -> Generated
```

`IUblDocumentGenerator` is provider-independent by construction (spec §3):
it has no knowledge of GİB, a specific entegratör, an HTTP endpoint, or a
signing certificate. It only ever sees R3 domain rows and produces a
canonical XML string; `ElectronicDocumentDispatcher`/`IElectronicDocumentProvider`
(Phase 3) are what eventually send it, unchanged, to a real provider.

## Field mapping

| UBL element | R3 source |
| --- | --- |
| `cbc:UBLVersionID` | constant `"2.1"` |
| `cbc:CustomizationID` | constant `"TR1.2"` (current GİB UBL-TR customization id) |
| `cbc:ProfileID` | `EArchiveInvoice` → `EARSIVFATURA` (fixed); `EInvoice` → `account_einvoice_profiles.invoice_scenario` mapped to `TEMELFATURA`/`TICARIFATURA`/`IHRACAT`/`KAMU` |
| `cbc:ID` | `ElectronicDocument.DocumentNumber` (= `sales_documents.document_no`, allocated once at posting - spec §9, never regenerated here) |
| `cbc:UUID` | `ElectronicDocument.Uuid` - generated once at `CreateOrGetForSourceWithinTransaction` (Phase 5), never regenerated by this generator even across repeated `Generate()` calls (verified by `RegeneratingReturnsTheSameCanonicalUuidEveryTime`) |
| `cbc:IssueDate` / `cbc:IssueTime` | `ElectronicDocument.IssueDate`, split into date/time, `CultureInfo.InvariantCulture` |
| `cbc:DocumentCurrencyCode` | `sales_documents.currency_code` |
| `cac:AccountingSupplierParty` | `companies` + `electronic_document_company_profiles` (Phase 6 added the address columns here - see Gaps) |
| `cac:AccountingCustomerParty` | `accounts` + `account_tax_profiles` + `account_addresses` (default, active) + `account_einvoice_profiles` |
| `cac:InvoiceLine` (one per `sales_document_lines` row) | `ProductId`→`Item/Name`+`SellersItemIdentification`, `base_quantity`→`InvoicedQuantity` (unit-converted quantity, not the raw invoice quantity), `unit_price`→`Price`, `net_amount`/`vat_amount`/`vat_rate`→`TaxTotal` |
| `cac:LegalMonetaryTotal` | `sales_documents.subtotal/discount_total/tax_total/grand_total` (domain-calculated at posting time - see `LocalSalesService.CalculateLine`; this generator never recalculates totals, only reads them) |

Buyer identification: `account_tax_profiles.person_type == "Individual"`
with a non-empty `accounts.identity_number` → `schemeID="TCKN"`;
otherwise → `schemeID="VKN"` using `accounts.tax_number`.

## Snapshot semantics

The generator reads **live** `Account`/`Company`/`Product` data at
generate time, not the minimal `ElectronicDocument.RecipientSnapshotJson`
captured at posting (Phase 5). That's deliberate, not a contradiction of
spec §5's "don't stay live-linked forever": immutability is enforced at
the *payload* level (`SavePayload` refuses to overwrite a UblXml/SignedXml
payload once the document is past `Generated` - see the Phase 2 review-gate
fix), not by restricting what the generator is allowed to read. Once the
XML is generated and saved, it is frozen; a later `Account.Name` edit
cannot touch it, exactly as required.

## Known gaps (reported, not silently worked around)

- **Seller/buyer excise (ÖTV) and withholding (tevkifat) tax are not
  modeled anywhere** - `sales_document_lines` only has `vat_rate`. This
  generator only ever emits a `KDV` `TaxCategory`/`TaxScheme` (Name="KDV",
  TaxTypeCode="0015"). An invoice that actually needs ÖTV or tevkifat will
  produce an incomplete XML; there is no silent substitution.
- **No `cac:PartyTaxScheme`/tax office element on either party.** The
  seller has `companies.tax_office`; the buyer has no equivalent tax-office
  field anywhere in `account_tax_profiles`. Rather than emit a
  `PartyTaxScheme` with a real VKN/TCKN but a fabricated or missing office
  name, the whole element is omitted for both parties. `PartyIdentification`
  (the VKN/TCKN itself) is still always present and correct.
- **No official GİB UBL-TR XSD bundle is available in this repo**, so
  `Validate()` is structural only: required elements present (ID, UUID,
  IssueDate, at least one InvoiceLine), UUID matches
  `ElectronicDocument.Uuid`, `PayableAmount` reconciles with
  `sales_documents.grand_total`, and line count matches. It does **not**
  validate against the real GİB schema - that requires the actual XSD
  files, which aren't bundled here.
- **Unit code mapping (UN/CEFACT Rec. 20) is a small, explicit table**, not
  a complete lookup: `ADET→C62, KG→KGM, GR→GRM, LT→LTR, MT→MTR, M2→MTK,
  M3→MTQ, KUTU→BX, PAKET→PK, ÇİFT→PR`, falling back to `C62` for anything
  else. Extend `UblInvoiceGenerator.UnitCode` as R3's real unit catalog
  grows past this list.
- **`cbc:InvoiceTypeCode` is always `"SATIS"`** - R3 has no return/credit
  invoice document type yet (see `docs/architecture/POSTING-ENGINE.md`'s
  Sales Return note), so there is nothing else it could correctly be.

## Validation

`Validate()` parses the generated XML back and checks: `ID` non-empty,
`UUID` equals `ElectronicDocument.Uuid` exactly, `IssueDate` non-empty, at
least one `InvoiceLine`, `PayableAmount` within 0.01 of
`sales_documents.grand_total`, and line count matches
`sales_document_lines`. A failure throws `UblGenerationException` - the
XML is never returned (and therefore never saved as a payload) if it
fails these checks.

## Tests

`tests/R3.Domain.Tests/UblInvoiceGeneratorTests.cs`: generates from a real
posted invoice and checks header/line/total mapping end-to-end including
the actual discount+VAT arithmetic (not just presence of elements); EInvoice

VKN; UUID stability across repeated `Generate()` calls.
